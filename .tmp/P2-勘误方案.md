# P2-1 勘误字段方案（数据结构变更，需用户过目后实施）

## 背景（对抗式审查 #10/#11）

现状：`original` 铁律名义上「逐字不可变」，但历史上已发生多起修改（OCR 错字修正、
[29.mp4] 清理、tut-003 重做等），全部只在 commit message 里留痕——数据本体无痕。
后人拿到库无法知道 original 是否被改过、改了哪、为什么改。

## 方案：登记表挂 meta（不动条目本体）

在 `meta.勘误登记` 新增登记表（数组），每条：

```json
{
  "日期": "2026-08-26",
  "条目": ["gen-642", "gen-643"],
  "类型": "噪音清理",
  "详情": "删除源 md 的 [29.mp4][37.mp4] 视频引用占位（网页无意义）",
  "commit": "440b411",
  "旧指纹": ["abc123", "def456"]
}
```

**不改条目结构**（不加 status/replaced_by 到每条数据），理由：
1. 313 条 data + 633 条 general，每条加字段体积膨胀且要动全库指纹
2. 真正需要勘误的是极少数（预计 <30 条），登记表挂 meta 零成本
3. check() 已读 meta，加一条校验轻量

类型枚举：OCR修正 | 噪音清理 | 重构拆分 | 补全 | 字段修正 | 语义去重

## check() 新校验

- `meta.勘误登记` 存在时：格式校验（日期/条目/类型/详情 必填，类型在枚举内）
- 有勘误登记的条目，指纹以「修改后」为准正常校验（现状即如此）
- 任何人可用登记表 + git 历史还原修改前状态

## 导出

不渲染勘误表（AI 协作元数据）。`ai_doc()` 导出时附勘误登记节。
